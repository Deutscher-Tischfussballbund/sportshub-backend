# Design docs

Reference and decision records for sportshub-backend. Read roughly in number order —
domain model first, then authorization, then policies and ops. Living **model** docs are the
source of truth for what the code does; **decision** docs record why a choice was made.

| # | Doc | Kind | What it covers |
|---|-----|------|----------------|
| 01 | [Competition & registration model](./01-competition-and-registration-model.md) | model | The `Season → Competition → Discipline → Stage → Pool → Round → MatchDay` tree; placement (TeamParticipation) vs. roster (RosterEntry) and the roster lifecycle. |
| 02 | [Role concept](./02-role-concept.md) | model | The roles and scopes (admin / region / club / team / competition) and what each may do. Central questions (6.1–6.3) resolved as built (team self-service, system-enforced rules); still open: uploader roles, reading role assignments, who may appoint region admins. |
| 03 | [Authorization model](./03-authorization-model.md) | model | The canonical scoped, hierarchical RBAC we run — how a decision is computed by walking a resource up the domain tree to a matching grant. |
| 04 | [Authorization: ACLs vs. scoped RBAC](./04-authorization-acls-vs-scoped-rbac.md) | decision | Why per-object ACLs are the wrong fit and, if fine-grained authz is ever needed, why a ReBAC engine (not Spring ACL) is the evolution. |
| 05 | [Season archiving & deletion](./05-season-archiving-and-deletion.md) | decision | State-aware delete + archive: hard-delete a result-free season, refuse (409) one with results and archive instead. |
| 06 | [Frontend topology: team portal vs. admin app](./06-frontend-team-portal-split.md) | decision | Build the team roster/results surface in the admin app now (extraction-ready), not as a separate portal yet; the clean seam for a future split. |
| 07 | [Prod Keycloak & admin bootstrap](./07-prod-keycloak-and-admin-bootstrap.md) | ops | Keycloak wiring and the config-driven bootstrap admin for production. |
| 08 | [Member self-service registration](./08-member-registration.md) | decision | Deferred DTFB-ID account-claim flow: the "inverted seam" (backend attests, Keycloak creates the user), the invite variant, and the blocking directory-vs-Keycloak question. |
| 09 | [League model (split from tournaments)](./09-league-model.md) | model + decision | **Implemented** (tournaments still parked): separate the league and tournament concerns instead of one overloaded tree. First-class `Tier`, a reusable typed `LeagueRuleSet` (points/game-plan/scoring), tournaments parked behind a seam. Supersedes doc 01 §1.1. |
| 10 | [API consumers & authorization](./10-api-consumers-and-authz.md) | decision | Serving multiple frontends: authz is identity-based (`dtfb_id` → DB roles), client-agnostic, so new consumers are Keycloak+CORS config, not code. Keep the core to domain resources + projections (not screen-shaped BFF endpoints). Audience gating settled; machine access via read-only API keys (doc 20). Public read tier decided 2026-09-26: no anonymous access — public displays read via API keys. |
| 11 | [Placement board](./11-placement-board.md) | decision | **Implemented 2026-07-25**, with three deviations from the original sketch (see the doc): one tier at a time via a dropdown (not every tier stacked), dedicated Promote/Demote buttons (not a cross-tier drag), and a new "Clear tier" bulk action alongside Randomize — both gated on actual Round existence, not the unenforced `Group.groupState` label. |
| 12 | [Matchday/fixture scheduling](./12-matchday-scheduling.md) | model + decision | **Implemented 2026-07-26, extended 2026-09-27** (backend + frontend). A circle-method round-robin generator (single/double) plus two real-world scheduling conventions — admin day-batch assignment vs. a team propose/accept negotiation within a round window (only there) — configured per `LeagueRuleSet`. Fixed kick-off slots with venue (tournament weekends), gap between rounds, deleting a plan, a schedule view, and region venues (SPO-56/75/77). |
| 13 | [VPS test deployment](./13-vps-test-deployment.md) | ops | Standing up the full stack (sportshub-backend + dtfb-frontend-ng + Keycloak + MySQL, fronted by nginx) for real testers — the corrected, as-executed deployment runbook. |
| 14 | [Team versioning, the User/Player split, and entity history](./14-team-player-versioning.md) | model + decision | **Implemented.** `Team` becomes season-scoped (copied per season, like League/Tier/Group) so a rename never rewrites past-season history; `Player` splits into permanent `User` (login identity) + `Player` (competitor record, NOT season-scoped); `Player`/`Club` stay single rows and instead get a generic `entity_history` change log, reconstructible "as of" a point in time; `LeagueRuleSet` edits are now refused once a closed season uses them (was a convention, now enforced). `League` got the same cross-season identity on 2026-09-26 (`leagueIdentityId`, SPO-28) so league admins keep their league across seasons. |
| 15 | [Player↔Club membership](./15-club-membership.md) | model + decision | **Implemented.** A first-class `ClubMembership` (joined_at + soft-delete left_at) is now the precondition `RosterService#addPlayer` enforces before rostering a player onto one of a club's teams — independent of, and prior to, team rosters. `GET /v1/admin/players` gained real server-side `clubId`/`regionId`/`q` filtering. |
| 16 | [Root federation (DTFB) and narrow cross-federation authority](./16-root-federation.md) | model + decision | **Implemented.** `Federation` becomes a general self-referencing tree; exactly one root (seeded `fed-dtfb`). A club may field a team in a root-level (national, e.g. Bundesliga) league and a separate team in its own sub-federation's regional league — already worked with no schema change. The root federation's admin gets narrowly-scoped authority over root-level teams/rosters for any club, never general authority over a sub-federation's own affairs (a broader design was considered and rejected). |
| 17 | [Result entry & confirmation](./17-result-entry-confirmation.md) | decision | **Decided 2026-09-21, backend built 2026-09-28 (SPO-15), frontend pending (SPO-57).** Either team records a match result; it becomes official only on confirmation by the opposing team, and each edit re-opens the cycle. Mutual confirmation freezes the result — thereafter only a league/federation admin may change it, and an admin may enter/edit/confirm at any point. Line-ups and substitutions stay on paper for the first release. **Refinement proposed 2026-09-28** (awaiting team confirmation): every team member may enter, but only the captains (`team_admin`) confirm; final once each side's captain agreed to the current version; club admins act as their team's side, not as neutral admins. |
| 18 | [Player gender](./18-player-gender.md) | model + decision | **Implemented.** `Player.gender` becomes the `PlayerGender` enum (`MALE`/`FEMALE`/`DIVERSE_MEN`/`DIVERSE_WOMEN`) — "divers" split by the league side it competes on. The side is admin-only (`PlayerDto.genderDetail`, any admin role); everyone else sees the public `gender` (`male`/`female`/`diverse`). League gender eligibility filtering is the planned next step. |
| 19 | [Category eligibility](./19-category-eligibility.md) | model + decision | **Implemented.** `Category` becomes an eligibility profile of nullable criteria enforced on roster add and submit (`409 PLAYER_NOT_ELIGIBLE`). First criterion: `eligibleSide` (men's/women's side via `PlayerGender.leagueSide()`, so divers players play their recorded side). Player name/birth year/gender became mandatory and `Category.shortName` unique in the same pass (V11). Age classes (U16/U19/seniors) are the next criterion on the same profile. |
| 20 | [API keys](./20-api-keys.md) | decision | **Implemented.** Machine consumers get backend-issued, read-only API keys (`X-API-Key`, only the SHA-256 hash stored, shown once) instead of Keycloak clients + write-capable grants. One filter enforces `GET`/`HEAD` only and no `/v1/admin/**` or `/v1/auth/**`; writes always need an identifiable user. Supersedes doc 10 §5's app-level write grants; `dtfb-service` retired. |
| 21 | [Rule sets as blueprints](./21-rule-set-blueprints.md) | model + decision | **Implemented 2026-09-26 in PR #78, to confirm 28.09. before merge.** `LeagueRuleSet` becomes a federation blueprint library; each league (optionally a tier) gets its own snapshot copy at creation/copy-forward, editable while the season runs and frozen once it ends. Resolver shrinks to `tier ?? league`. Replaces doc 14's lock-and-clone (which missed ended-but-unarchived seasons, the federation-default fallback and cross-season sharing); realizes B-2026-08-17-1. |
| 22 | [Fixture modes](./22-fixture-modes.md) | decision | **Decided 2026-09-29 (Marvin), to confirm with Daniel (SPO-58); backend and frontend built.** Rule sets get a `fixtureMode` profile: `RACE` (Race to N — one running score over the game plan's segments, each ending at the next step 6/12…42; end rule draw-allowed or two-point lead; the M1 mode) or `GAMES` (sets per game, later). Entry = running score per segment, checked; byes become scored fixtures (bye score per blueprint, e.g. 42 : 30); the DTFB (root-federation admins) is the tournament management; table points → goal difference → head-to-head; an enforced confirmation deadline (e.g. 15 min), after which only the tournament management confirms. |
| 23 | [Line-ups and substitutions](./23-lineups-and-substitutions.md) | decision | **Proposed 2026-09-29 (Marvin), reverses B-2026-09-21-11; to confirm with the team and Daniel; backend and frontend built.** Each captain enters the line-up (players per game, from the roster) before kick-off, hidden from the opponent until both are in, then locked. Substitutions become `MatchEvent`s of type `SUBSTITUTION` (`playerIn`/`playerOut`, positional) — the start of an event log for goals, timeouts, cards and a future referee role. Results need both line-ups (rule-set setting `lineupRequired`, on by default), except for neutral admins. |

The current database model (dbdiagram.io DBML) lives in [`dbdiagram.io/current_model.txt`](./dbdiagram.io/current_model.txt) — keep it in sync with schema changes.

Numbers are a reading/topic order, not a chronology — renumber on the rare insert.
